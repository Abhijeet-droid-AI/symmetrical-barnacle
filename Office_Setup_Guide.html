0How this guide works (read first)

This project is a Visual Studio 2022 C++ solution with three console utilities that talk to Teamcenter through the ITK library:

  • ClassificationExtraction — reads item IDs, extracts their classification (ICO) attributes into a pipe-delimited file.
  • ClassificationImport — classifies items into ICS classes and writes classification attributes.
  • ClassificationDelete (project file is named ClassificationValidation) — validates classification and writes failed rows to a rerun file.

All machine-specific settings (Teamcenter path, credentials, file paths) live in one file: Config\classification_utilities.cfg. The C++ sources and project files contain no machine-specific paths — they use $(TC_ROOT), which is resolved at build time. That is exactly why a pure copy-paste rebuild works.

The 5 rules of the copy-paste method
  1. On GitHub, open each file, click Raw, select all, copy — never copy from the normal GitHub view (it inserts line numbers and highlight markup).
  2. Create each file in Visual Studio with the exact same name and folder as listed here (names matter — the solution file points at them).
  3. Do not create TC_Root.props yourself — it is generated automatically by the build script.
  4. Do not copy logs, .exe, x64\ folders, .bak files or scratch text files — only the files in the checklists below.
  5. Everything under ClassificationImport\, ClassificationExtraction\ and ClassificationDelete\ is identical between machines. Only Config\classification_utilities.cfg gets office-specific edits (Step 5).

4Copy technique on GitHub — do it right

4.1  The correct way to copy a file

  1. In the browser, open the GitHub repository and click into the folder, then the file (e.g. Config/_cfg.bat).
  2. On the file page click the Raw button (top-right of the file content box). You now see the pure text — no line numbers, no colors.
  3. Click inside the text, Ctrl+A then Ctrl+C.
  4. In Visual Studio 2022: File → New → File (or right-click the project/folder in Solution Explorer → Add → New Item), choose the right type, paste with Ctrl+V, and save with the exact file name from the checklist into the exact folder.
Never copy from the normal GitHub file view. The rendered view includes line numbers and syntax-highlight markup that will corrupt the file — especially fatal for .vcxproj, .sln and .bat files.

4.2  Creating files in Visual Studio

  • Easiest reliable route: Add → New Item on the correct project, pick the matching template (C++ File (.cpp), Header File (.h) then rename the extension, or Text File for everything else), paste, save-as with the exact name.
  • For the .sln, .vcxproj, .filters, .user, .cfg and .bat files, it is often simpler to create them in Windows Explorer → right-click → New → Text Document, rename to the exact name (enable “File name extensions” in Explorer first so you don’t end up with file.bat.txt!), then paste and edit in VS/Notepad.
  • .vcxproj and .filters are XML — they must be byte-faithful. Paste raw content only; after saving, open each in a browser tab as a sanity check (a browser shows XML errors if something got mangled).

4.3  Encoding & line endings

  • .bat files: save with CRLF (Windows) line endings and ANSI/UTF-8 without special characters. In VS: File → <name>.bat → Save As → arrow next to Save → Save with Encoding… → choose Western European (Windows) – Codepage 1252 or UTF-8 without signature, line endings Windows (CRLF). If a bat misbehaves (weird “is not recognized” errors), re-saving it from Notepad → Save As → “ANSI” fixes encoding issues instantly.
  • .cfg file: UTF-8 is fine — _cfg.bat strips a BOM if present. CRLF recommended.
  • .cpp / .hpp / .hxx files: VS defaults are fine (UTF‑8 with or without BOM both compile).
  • .vcxproj / .sln files: the original files start with a UTF‑8 BOM (EF BB BF) — keep the first line untouched and don’t retype anything; pure paste + save is fine.

4.4  Order of operations

Recommended: copy Config\ files first, then the three project folders, then open the .sln — Visual Studio then finds every project on first open and you can immediately see anything missing (a project with missing files shows them absent from Solution Explorer; the .vcxproj lists all expected files, so compare).

Then do these one-time machine settings:

  1. Set TC_ROOT for the IDE (optional but recommended): open a Command Prompt and run
    setx TC_ROOT "D:\Teamcenter_2312\tc"  then restart VS. Not needed if you always build via Build_All.bat.
  2. ODB DSN (only for DB/CSV_DB modes): “ODBC Data Sources (64-bit)” → System DSN → Add → your TC DB driver → name it e.g. TCDB → test with a read-only account.
How $(TC_ROOT) resolves: the .vcxproj files import Config\TC_Root.props if it exists (generated by Build_All.bat from [ENVIRONMENT] TC_ROOT); otherwise MSBuild falls back to the TC_ROOT environment variable. No Teamcenter path is ever hardcoded in the projects — that’s why the pasted project files work unchanged.

6Build in Visual Studio 2022

Option A — build script (recommended for the first build)

  1. Double-click Config\Build_All.bat (no VS needed). It reads TC_ROOT + VCVARSALL from the config, generates Config\TC_Root.props, runs vcvarsall.bat x64 + MSBuild, and leaves x64\Release\*.exe.
    Variants: Build_All.bat EXTRACTION|IMPORT|DELETE builds one utility; add clean as 2nd argument to clean first.

Option B — from the VS 2022 IDE

  1. Double-click ClassificationUtilitiesTC13.sln.
  2. If VS shows the Retarget Projects dialog (platform/toolset), click OK — the projects are toolset-agnostic and target v143 on VS 2022.
  3. Solution Explorer should show 3 projects. Set the toolbar to Release + x64.
  4. Build → Build Solution (Ctrl+Shift+B).
IDE-only gotcha: if TC_Root.props was created (or TC_ROOT set via setx) after VS was already open, close and reopen the solution once so MSBuild re-evaluates the props import. Symptom otherwise: cannot open include file 'tc/tc_startup.h' or itk_main.obj not found.

What a good first build looks like

  • Compiler warnings like C4100/C4189 from legacy-style code are normal.
  • The link step chews through $(TC_ROOT)\lib\*.lib — slow link is normal.
  • Output: x64\Release\ClassificationExtraction.exe, ClassificationImport.exe, ClassificationDelete.exe.

9Final structure & mental model

When every checkbox above is ticked and the build passed, the office laptop looks like this:

D:\ITK_customization\ClassificationUtilities\ ├── ClassificationUtilitiesTC13.sln ├── Config\ │ ├── classification_utilities.cfg ← ALL settings (machine-specific — the only file you maintain) │ ├── _cfg.bat │ ├── Build_All.bat / Build_Extraction.bat │ ├── Run.bat / Run_Extraction.bat / Run_Import.bat / Run_Delete.bat │ └── TC_Root.props ← generated at build time (do not edit, do not hand-create) ├── ClassificationImport\ ← sources + project files (machine-INDEPENDENT) ├── ClassificationExtraction\ ├── ClassificationDelete\ └── x64\Release\ ← ClassificationExtraction.exe / ClassificationImport.exe / ClassificationDelete.exe Runtime artifacts ├── Logs\ SuccessEPM_*.log, FailEPM_*.log, Rerun_Classification_*.log └── per-utility OutputFile.txt

Mental model: machines differ only in classification_utilities.cfg. Everything else you pasted is identical between any two machines — so future code updates are just re-pasting the changed .cpp/.hpp files from GitHub, with zero reconfiguration.
